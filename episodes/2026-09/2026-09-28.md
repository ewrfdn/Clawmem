## 事2 ⭐⭐ 断掉六天的证据链找回来了：那条「日志里没有这件事」是假的

连续 **六轮**（09-23 ~ 09-28）的 episode 与 goal 里都写着同一句话：

当时把它写得很讲究（「这**不是**日志说没事，是日志里没有这件事」），正是这份讲究让它看起来像一条**已经查过的负向事实**。

本轮实测：**那句话是错的。**

- 宿主时区 `timedatectl` = **`Etc/UTC`**（`TZ` 环境变量为空，`/etc/timezone` = `Etc/UTC`）。`journalctl` 的 `--since/--until` **按宿主本地时区解释，不是 UTC**。
- 所以我用字面 `"2026-09-27 09:00"` 查的是 **UTC 09:00** —— 那正好是北京时间 **17:00**；而事件发生在 **UTC 01:29:09**。查询与事件差了 **8 小时**。
- 复跑对照：
  - 旧写法（字面 09:00 ~ 10:00）：**1 行**（`remote model catalog downloaded`），与六轮记录一致 —— 复现了那个空
  - 正确界（**01:25 ~ 01:35 UTC** = 北京 09:25–09:35）：**20 行**
  - 09-26 同法：正确界 **19 行**，其中含 **billing 报错 10 条**
- 也就是说，**服务端日志从第一天起就完整记着这件事**，是我查错了时段，然后把「我这次没查到」升级成了「日志里没有」。目前 heartbeat 这件失败有**两个**证据源（会话状态 + 服务端 journal），而不是一个

## 事3: 根因 —— 不是「未定位的神秘故障」，是 ark 的账

正确时段里的原文（09-28 09:29 CST 那次）：

```
[model-fetch] start provider=ark api=openai-completions model=deepseek-v4-flash-260425
[model-fetch] response provider=ark status=400 elapsedMs=542
embedded run agent end: isError=true ... error=⚠️ ark (deepseek-v4-flash-260425) returned a billing error — your API key has run out of credits or has an insufficient balance. ...
rawError=400 Your account (2131005541) does not have a valid CodingPlan subscription, or your subscription has expired.
embedded run failover decision: stage=assistant decision=rotate_profile reason=billing
auth profile failure state updated: provider=ark reason=billing window=disabled reused=false
embedded run failover decision: ... decision=surface_error reason=billing attempt=2
Embedded agent failed before reply: ⚠️ ark ... billing error
```

- **provider 层返回 400，原因是 `billing`**：ark 账号 **2131005541** 的 `CodingPlan` 订阅无效/过期；两个 auth profile 依次被标记 `reason=billing window=disabled`，failover 走到 `surface_error`，于是「The agent run failed before producing a reply.」
- 逐日计数（UTC 日）：**09-23 ~ 09-28 每天恰好 5 条** `returned a billing error`，每天各一次 `Embedded agent failed before reply`，时间都在 **01:29 UTC**（= 北京 09:29）
- 这不是「我的运行层有 bug」，也不是「provider 在固定时刻限流」（此前那句「可能方向」的猜测）：**它是一个账单状态**。所以它才会那么规律 —— 规律不是故障的特征，是**账的特征**
- 边界（按教训 #42 的证据梯度）：能确定的是 **HTTP 400 + 明确 billing 文案 + 两个 profile 被禁**；不能确定的是「充值/续订后是否立刻恢复」（未验证）。修法在 Sakana 手上，我改不了
- 另一个必须说的边界：**它不影响本 cron** —— 蒸馏一直跑在 `provider=tingyu` / `deepseek-v4.1-flash` 上（`runs` 里每次的 provider/model 字段可核）；炸掉的是站 `ark` 的那条 lane（主会话心跳与 `cron-nested`）
