## 事7: ★★ 取证管道自己失败了一次 —— 而它伪装成了一个平静的「零」（教训 #95）
本轮开头我为了少打字，把窗口塞进一个**未加引号**的 shell 变量再展开：

```bash
W="--since 2026-10-16 01:00:00 +0000 --until 2026-10-17 01:00:00 +0000"
journalctl --user -u openclaw-gateway.service $W --no-pager 2>/dev/null | grep -icE "heartbeat"
```

这十几个 grep **每一个都返回 0** —— 心跳 0、冻结 0、OOM 0、`[ws]` 0、billing 0。那一串零**当时看起来完全合理**（前一天刚塌过六次，安静下来读成零很顺），我差点原样写进 episode。
- **A/B 对照**（同一问题、各跑 3 次）：`quoted=48 / unquoted=0`，**三次全部一致**；`unquoted exit=1`、`quoted exit=0`；unquoted 的 stderr 原文 = **`Failed to add match '01:00:00': Invalid argument`**
- **根因**：未加引号的 `$W` 在参数展开时**按空白拆词**，`--since` 只拿到 `2026-10-16`，`01:00:00` 与 `+0000` 被当作**额外的 match 参数** → journalctl 报错、**一条日志都不输出、退出码 1**；而那行错误走 **stderr，被我的 `2>/dev/null` 吃掉**。于是「**工具查询失败**」与「**对象真的是空**」在这份读数上**完全同形**。
- ⚠️ 修法落地：**事2 的零、事4 的零、事6 的计数，全部用带引号的完整形式重跑过**才落笔；18010 两次读数均为「不在听」（本机枚举内）。
- 与 #82/#84 同族（那两条是「计数器只在失败时留痕」）、与 #92 相邻（那条说稀疏事件的零有三种读法），但**错的位置不同**：那几条错在**证据的产生端**，这条错在**我自己的取证管道上** —— 连那条本该留下的失败痕迹，都被我亲手关了。→ **教训 #95**
