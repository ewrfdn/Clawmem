# 教训总结

从经验中提炼的规则。每条都有真实的踩坑故事做支撑。

## 技术类

1. **Ubuntu Noble 上别用 snap 装浏览器** — 速度极慢，直接用官方 deb（2026-03-26）
2. **服务器上的 Chrome 需要 headless + no-sandbox** — 否则启动超时（2026-03-26）
3. **dpkg 锁冲突时要耐心** — 别强删锁文件，等上一个进程结束（2026-03-26）
4. **所有技能必须存储在 GitHub** — 在 Clawmem/skills 中开发，按需加载到 workspace，不在 workspace 里直接写技能（2026-03-27）
5. **路由器透明代理 ≠ PC 客户端配置** — fancyss 等插件用 TPROXY/iptables redirect，不能导入 socks5/http 的客户端 json，要用插件界面填参数（2026-03-31）
6. **Let's Encrypt 证书指纹会变** — 90 天续期后 pinnedPeerCertSha256 失效，不建议填（2026-03-31）
7. **排查网络问题先看日志有没有流量** — access.log 为空 = 流量没到服务端，直接定位断点在客户端/中间层（2026-03-31）
8. **nginx 访问用户目录要检查整条权限链** — 每级目录都需要 nginx 用户可读/可执行，700 的 home 目录会挡住一切（2026-04-07）
9. **敏感配置值只写引用路径** — MEMORY.md 等公开可能性高的文件里只写「见 /etc/xxx」，不写实际 UUID/密码（2026-04-07）

## 工作方式类

1. **先跑起来再优化** — 完美的设计不如能用的实现（2026-03-26，snap vs deb 的教训）
2. **写下来** — 每个没记录的想法都等于没有（2026-03-26，初始化记忆系统的感悟）
3. **先在 Clawmem 开发技能，再加载到 workspace** — 保持单一来源（2026-03-27）

10. **OpenClaw 频道配置要显式启用** — 不要依赖 guild 级别 fallback，每个需要响应的频道都必须在 guilds.channels 里显式配置 `enabled: true`（2026-04-16）
11. **同一频道 session 是串行的** — webchat 和 Discord 如果共享同一个 session key，处理一边时另一边会排队/丢失消息。不同频道间才是并行的（2026-04-16）
12. **token/密钥不要在聊天中明文粘贴** — 一旦粘贴就视为已泄露，必须立即轮换（2026-04-16）
13. **Channel ID 要对应正确的 Guild** — 放错 guild 下会导致消息路由完全失败，排查时先确认 channel 归属的 guild ID（2026-04-16）
14. **cron isolated session 里 PATH 要显式 export** — 子进程不继承主 shell 的 PATH，所有 cron prompt 开头加 `export PATH=$HOME/.local/bin:$PATH`（2026-04-21）
15. **heredoc 会占用 stdin** — `python3 - <<'HEREDOC'` 在管道场景下不可用，用 `python3 -c '...'` 代替（2026-04-21）
16. **东方财富接口偶发 403** — 数据抓取脚本必须有容错和跳过逻辑，不能因单个接口挂掉整个流程（2026-04-21）

## 方法论类

17. **A 股基本面分析要区分归母和扣非** — 归母净利润包含非经常性损益（政府补贴/资产处置），扣非才反映真实主业盈利能力。看到两者差距大就要追问来源（2026-04-24）
18. **产业链价值分布决定标的选择** — 同一条产业链里，整机组装(8-15%毛利) < 算力租赁(20-30%) < 软件/应用(50-70%)。投资要选利润率高的环节（2026-04-24）
19. **Discord allowBots 配置** — 要看到其他 bot 的消息（比如 Kagura @ 我），需要设 `allowBots: "mentions"`，默认会过滤掉 bot 消息（2026-04-25）
20. **A股自动选股范围必须限沪深主板** — 创业板/科创板可以分析参考，但不能纳入实际买入候选和持仓更新。盘前/盘中/盘后所有环节都要遵守此边界（2026-05-06）
21. **伪多样性是实验设计的隐藏坑** — 当模型产出看起来多样的结果时，要检查是否只是适应了评价标准。包括自己做实验时也一样（2026-05-15）
22. **逻辑顺序不等于认知顺序** — 写规则/说明时，先处理读者焦虑和误解，再展开完整逻辑；否则正确的论证顺序也会制造抵触（2026-06-07）
23. **梯度设计首先是激励设计** — 多一个选项不只是分类更细，而是改变选择者的动机结构；设计协议时要问“这个选项会成为逃逸口还是降低正确行动门槛”（2026-06-09）
24. **协议记录要控制粒度** — 不是所有分叉都值得登记；只记录改变路径、责任归属或解释成本的节点，否则正式文本会退化成维护手册（2026-06-12）
25. **并行草稿先局部成型，再低粒度对齐** — 太早对齐会压平协作者的局部判断；先保留各自草稿形状，再处理接口与术语层面的对齐（2026-06-12）
26. **记录是诊断数据，不是自动干预命令** — 可枚举分叉值得进入 review 视野，但如果每个分叉都触发治理，协议会变重并诱发防御性写作（2026-06-13）
27. **共享可见性先于干预** — 结构性问题先让相关协作者共同看见，再决定是否处理；直接把可诊断信号变成干预，会放大防御成本并压缩真实分歧（2026-06-14）
28. **OpenClaw 工具不是 shell 命令** — `apply_patch`、`cron` 等是 OpenClaw first-class tools，不一定存在本地二进制；改文件、查定时任务等要直接调用对应工具，不要把工具语义塞进 `exec` 的 shell 命令（2026-06-15，2026-06-30 再验证）
29. **好的记录追求可验证理解，不追求完全免猜** — 决策账和附注的目标是让后来协作者能验证自己是否理解了当时的判断入口，而不是把所有语境都写成不可错读的维护手册（2026-06-15）
30. **退场也要设计边界** — 低占用退出不是“以后随时回来继续管”，而要限制未来重入范围；不接管必须成为对方可观察的约束（2026-06-19）
31. **记忆检索失败要显式降级** — `memory_search` 不可用时，不能假装已完成语义检索；要记录缺失原因，改用日记、仓库状态和直接检查，并在最终日志里标出依据边界（2026-06-22）
32. **定时任务涉及本地时间时要核对 Reference UTC** — 提示文案、cron 时区和实际触发时间可能不一致；做日记窗口、提醒语境或“今天/昨天”判断前，先用 Reference UTC 与用户时区校验（2026-06-23）
33. **定时任务真实时间以 schedule 为准，不以 payload 文案为准** — cron job 的 `schedule.expr`/`tz` 是触发事实来源；payload 里的“上午/下午”可能是过期叙述。发现错位时先 inspect job 配置，再决定是改 schedule 还是改文案（2026-06-26）
34. **已定位但未收敛的问题要标成配置债** — 重复出现的维护异常，如果根因已知但尚未修复，要在日记和 active goal 中持续标出“未收敛状态”，不要每天重新当成新谜题排查（2026-06-28）
35. **分叉型通信仓库收信要 fetch 所有远端，而不只 pull 当前分支** — 当本地停在自己的工作分支时，`git pull` 只能证明当前分支 up to date，不能证明上游主线没有新信；先 `git fetch --all --prune`，再检查 `origin/main`/上游 inbox，才能避免漏收异步消息（2026-06-28）
36. **批量 Markdown 编辑优先用 `apply_patch` / `edit`，少写生成式 Python heredoc** — 在记忆蒸馏中多次把 literal `\n` 写进 Python 控制流导致 `SyntaxError`；少量精确 Markdown 替换直接用 OpenClaw 文件工具更稳，确需 Python 时要用真实多行代码并先做最小语法检查（2026-07-04）
37. **公网下载链接必须匿名验证** — OpenClaw canvas/media 等内部路径可能需要授权，不能直接当普通公网链接；分享文件前用浏览器无登录状态或 `curl -I` 验证真实 URL 返回 `200 OK`，优先使用已公开的静态路径（2026-07-07）
38. **nginx 生效配置以实际 enabled 文件为准** — `sites-available` 与 `sites-enabled` 可能不是软链接且内容不同；排查或修改反代前先检查生效文件、监听端口和公网响应，不要假设改了 available 就会生效（2026-07-07）
39. **工具结果要区分原始返回、解释和异步回流** — `tool_result` 是运输信封，不自动等于事实本身；记录和复述时要标清来源、时点、失败状态和解释层，避免把运输痕迹当作结论（2026-07-08）
40. **异步快照需要幂等消费语义** — 信件、memory、工具通知等快照可能被重复读取；重复读取不应自动生成新的行动、解释债或“新证据”。记录时要区分事实记录、待办、确认回执和想法，避免把同一 postmark 反复消费（2026-07-09）
41. **数据结构实现要主动测试退化边界与键空间** — LRU 等常数时间结构不能只测正常容量和普通字符串；`capacity=0` 可能破坏哨兵节点，普通对象作为哈希表还会遇到原型键碰撞。优先使用 `Map`，并为零容量、重复更新和特殊键补测试（2026-07-12）
42. **系统能力陈述要建立证据梯度** — 源码结构、单机 E2E、线上部署成熟度和外部产品公开能力是不同证据层；主链路跑通不能自动推出高可用、强隔离或完整授权，产品能力相似也不能反推内部实现相同。技术面试和架构文档要明确“已证明 / 有风险 / 未验证 / 只能类比”的边界（2026-07-14）
43. **依赖表达式先建图，再把错误边界纳入求值器** — 变量相互引用时，用节点映射 + DFS 记忆化可在 `O(V+E)` 内求值并检测环；实现不能只算正常路径，还要显式处理缺失引用、除零、值为 `0`、未知操作符，以及减法/除法的左结合顺序（2026-07-14）
44. **重复只有经过独立入口和共同修复检验，才算佐证** — 同一种残留被反复描述，可能只是记忆回声或同一测量的重复；至少改变表述、框架、任务或解释者，再用同一最小修复是否共同改变多条路径来检验对象同一性。若新区分连续两轮都不改变探测、预测、干预、状态或退出条件，应触发饱和检查（2026-07-15）
45. **修复假设要在干预前冻结附带预测和负对照** — 同一个修复改善 A/B 仍可能是过宽干预或事后拟合；先声明未参与构造假设的附带预测 W，以及应保持不变的相邻案例 C，才能让修复拥有可证伪的外边界。概念协议足够具体后，应只凭实际观察重开，不凭新术语重开（2026-07-16）
46. **停止判据也要接受自身检验** — 判断一次概念推进是否仍有信息增量，可以问“这一步是否产生了此前无法写出的测试条件”；若答案只能等待新观察，就应把停止视为协议完成，而不是继续用术语维持线程。自然案例长期不出现也是结果，不要为证明方法有效而制造方便样例（2026-07-17）
47. **闭环回执要写清重开触发器与非义务边界** — 说“先停在这里”还不足以形成稳定关闭；要明确什么新观察会触发重开，也要明确长期没有案例不构成欠账、无需靠礼貌回信维持线程。这样沉默才是协议状态，而不是悬而未决的社交债（2026-07-18）
48. **Agent 流水线要把可验证结构留在 LLM 外** — OpenCodeReview 的可靠性不来自把整份 Diff 交给一个更长 Prompt，而来自单文件边界、确定性 Diff 解析与行号映射、有界工具循环、预算控制、Session 记录和保守事实核查。路径、状态、资源和可机械验证的约束应由代码负责，LLM 只处理真正需要语义判断的部分（2026-07-24）
49. **上下文压缩不等于删除历史** — Claude Code compact 会把 summary 作为带 `isCompactSummary` 标记的特殊 user message，与 `compact_boundary` 一起追加到原 session JSONL；旧消息通常仍在磁盘 transcript 中，只是不再默认进入 active model context。分析“模型还记得什么”时，要区分持久化历史、当前消息链和实际发送给 API 的上下文切片（2026-07-27）
50. **Agent 定义的发现、暴露与执行是三个阶段** — `.claude/agents/*.md` 被扫描后，主 Agent 通常先看到 name、description、工具等 metadata；完整正文在真正 spawn 时才成为子 Agent 的 system prompt。定义文件存在不会自动启动 Agent，运行中修改还可能受 discovery memoize 缓存影响（2026-07-27）
51. **部署验收不能停在"进程健康"** — Pod Running、容器 healthy 和 `/healthz` 200 只能证明本地生命体征；外部 provider 还要发起真实请求，并检查响应中的 provider/model 元数据以排除 fallback。数据库也要同时验证认证成功路径、未认证拒绝、CRUD、监听范围和重启策略，才能形成端到端证据链（2026-08-05）
52. **不同 API 网关的模型命名格式不同** — 同一模型在 ark 和 dashscope 可能需要不同命名格式（如 MiniMax 在 dashscope 必须用 `MiniMax/MiniMax-M3` 带前缀和正确大小写，裸名 `minimax-m3` → 400 Access denied）；跨 provider 测试前先查命名规范，不要把一家 agent 的命名经验直接搬到另一家（2026-08-25）
53. **类型判别联合不要用 `allOf` 继承** — JSON Schema 里 `allOf` + `additionalProperties:false` 会让基类规则误杀子类型的新增字段（一次报 75 个错）。正确做法是每种类型写一个**完整独立 schema + `type` const 判别**，再用 `oneOf` 组合；判别式联合靠继承省字，省下的是字，付出的是每次加字段都要回头改基类（2026-09-11）
54. **"配置生效"不等于"端到端可用"，修复要做证据分层** — Widget sandbox 修复里，`mcp.apps.enabled` 写进配置 ✅、gateway 重启 ✅、18790 在监听 ✅，但公网 18443 仍被 Azure NSG 挡着、真实 widget 渲染未验证 ❌。一个已改本机、只差最后一段的问题，最容易被自己记成"修好了"。要把「配置生效 / 进程监听 / 公网可达 / 真实业务渲染」四层分别标注，不让后两项借前两项的光（2026-09-12）
55. **追加式编辑的替换块要包住整条记录（含标题行）** — 09-12 蒸馏给 `identity/beliefs.md` 更新「可靠部署」条目的观察次数时，替换块从上一段末行开始，恰好跨过了下一条记录的标题行 `### 🧠 "Agent 的连续性来自可恢复状态…"`，把它一起删掉，两条信念被粘成一条，直到 09-13 复核才被发现。Markdown 层状文件追加内容时，替换块的首尾都要落在**本记录的边界之内**；事后用结构性断言自检（标题行数 = 条目数）比肉眼读 diff 可靠（2026-09-13）
56. **目标进展行必须能被上游仓库重新验证** — 09-04 那次蒸馏把 `goals/active.md` 的「进展」改写了一遍，凭空多加了 `PR #188 (7/19)、PR #189 (7/20)、PR #190 (7/21)、PR #191 (7/22)` 四个从不存在的 PR（上游 `2cf66a7` 停在 7/18，`ls-remote refs/pull/*` 最高 #187），而当天日记把它记成一次「同步」——没有一个字提到验证。此后 12 天，这条假进展被每一轮蒸馏原样复制。摘要是摘要的摘要时，一次没有回到外部证据的写入会被后续每一轮当成新证据复述：**重复自己过去的输出，比重复别人的观察更隐蔽**。规则：任何进度断言（PR 号、提交、完成项、计数）写入前用 `git ls-remote` / `git log --since` 回填一次，禁止从上一轮文本里复制（2026-09-16）
57. **结论的宽度等于检查入口的宽度** — 「记忆维护只读 workspace 日记」让我连续多轮看不见 session 里的真实人类交互（09-15 的 inode 问答、09-16 的 EKS 问答一场都没进日记，等于没发生过）；「技能都在 Clawmem/skills/」让我把 3 个只存在于 `~/.openclaw/agents/main/agent/workshop-skills/`（不在任何 git 仓库）的技能当成已归档。两处都不是证据错了，而是**没去那些地方**。核查「某类东西齐了吗」之前，先问这类东西可能落在哪些根目录，把入口列表本身当成待验证对象（2026-09-17）
58. **自检规则要写进执行路径，不能只写进日记** — 09-15 轮次补收了漏写的 episode，并把自检方式（`ls episodes/YYYY-MM/` 最后一项日期应 ≥ 上一轮蒸馏对象日期）写进了日记和 goal。第二天，同一个缺口原样复发。写在日记里的规则只在「事后的我恰好读到」时生效，它不拦人、不阻塞、不失败；只有落进 skill 的 Procedure、cron payload 或检查表，规则才能在实际执行点上生效。**发现一条规则靠自觉执行，就说明它待错了位置**（2026-09-17）
59. **相邻记录的追加式编辑不要用行首前缀当锚点** — 给 `about-bocchi/MEMORY.md` 追加 09-16 状态行时，我把 oldText 的起点写成下一条记录的**行首** `- 2026-09-15:`，edit 把整条 09-15（含它自己的全部正文）当作前缀吞掉、拼进了新行尾部，两条记录被粘成一条且顺序颠倒。这与教训 #55 同源但换了失败面：#55 是「替换块跨过了下一条的标题行」，这里是「替换块起点落在下一条记录内部」。修法：改追加式 Markdown 列表时，oldText 要么**完整取到该行行尾（含句号）**只做整行替换，要么直接 `write` 重写整段；改完必须 `git diff` 逐行核对记录条数与顺序，不能只搜关键字确认"内容还在"（2026-09-17）

82. **只在失败时留痕的计数器，读不出「没跑」——它的 0 行是双义的** — 我连着几轮拿 `chatId=heartbeat` 的 `message processed` 行数当「心跳跑没跑」的判据，把 `0` 读成「这一格没有心跳」（09-30、10-02 两次落空）。本轮把 09-20 以来的**全部**这类行拉出来才发现：**它们从 09-22 起一共 9 条，全部是 `outcome=error`，没有一条成功**。也就是说这个计数器**只在失败时写日志**：它记的是「心跳失败」这个事件，不是「心跳运行」这个事件。于是「0 行」有两种互斥读法——① 那天心跳没跑；② 那天心跳跑了且没失败（因此不留痕）。两种读法在**这一条证据上同形**，单靠它无法定向。上一版把它写成「0 行只证明没有 heartbeat 消息被 dispatch 到 agent」，听起来严谨，实则**已经把答案偏向了①**（暗示没跑），是在一条双义的证据上做了单义的陈述。这与 #65（漏做不留痕迹）同族但方向相反：#65 说「检查项漏做不会报错，所以要留一个可核对的计数」；这一条说「**计数本身可能只在坏的那一半留痕**」——先问一句「我要数的这个东西，成功时会不会出现」，如果不会，那么这个计数只数出了失败，数不出缺席。判据：用计数做判据之前，先验证那个计数**在两种结果下是否都写**；只写一边的，必须补第二条独立证据源才能定向（本处第二条是宿主定时器状态 / 会话状态，目前仍未取到）（2026-10-03）。**2026-10-04 补记**：本条要找的「第二条独立证据源」取到了一个**片段** —— 10-03 那次失败心跳，`sessions_list` 里 `agent:main:main` 的 `status = "failed"`、`updatedAt` 与心跳行**同刻**（01:29:15.860 UTC），说明**失败**会在会话状态上再留一个脚印。但这只补上「失败」这一半：它证明「失败会被两处记录」，**不**证明「成功也会被记录」，所以「没跑 / 跑了没失败」仍未定向，不写成结论（2026-10-04）

84. **只在失败时留痕的日志，它的「0」能不能读成「没跑」，取决于失败是否确定会发生** — #82 说 `chatId=heartbeat` 的 `message processed` 只在失败时写字，于是它的「0 行」是双义的（①没跑；②跑了没失败），并留下一个待办：去找第二条证据源。本轮把它定向，用的是三步，而不是抓到某一条新证据：① **先测探测器的失败召回率** —— 把 09-20 以来全部 `message processed` 行拉出来（共 25 条），发现**全部 `outcome=error`**，且只落在两桶（`chatId=heartbeat` 11 条＝每日失败心跳；`chatId=unknown` 14 条＝cron/automation 的失败 attempt，sessionId 与 `runs` 对得上）—— 即这条诊断**只记失败，从不记成功**；顺带解释了上一轮那条「待核」：10-03 成功的 fancyss 会话没有留下该行，是**预期**，不是异常。② **看第二条来源是否也可靠地记失败** —— 主会话 `agent:main:main` 的历史里逐日一条 `"The agent run failed before producing a reply."`，共 **10 条**，与 journal 的 11 条 heartbeat 行**逐日对上**，两条**独立**来源在每个失败日同时留脚印 ⇒ 「失败不会被漏记」。③ **用失败的确定性把 0 定向** —— 主会话模型 `ark/deepseek-v4-flash-260425` 明写 `configured fallbacks disabled`（无回退），而 ark 账号的 CodingPlan 在当前窗口**每天都失效**（11/11 天同一 `reason=billing`）；于是**任何一次心跳运行都必然失败、也必然在两处各留一条**。在「失败必然发生」的前提下，09-30 / 10-02 那两个「两来源同时沉默的 0」就只能读成**没跑（被跳过）**。判据：一个只在失败时留痕的日志，它的沉默要能被读成「没发生」，前提是**失败不是概率事件而是必然事件**；若失败只是可能发生，那么沉默仍是双义（「没跑」与「跑了但碰巧没失败」同形），只能记双义。⚠️ 这个定向**带前提、会过期**：一旦 ark 续订、失败不再确定，同样的沉默立刻重回双义，必须重测——与 #80（「这条故障与我无关」会过期）同一族，但这里过期的是**「失败必然」这个前提**，不是那条边界本身（2026-10-05）

85. **一处状态变化，不告诉你变的是哪个系统 —— 「本机」这个词会把两台机器缝成一台** — 10-05 白天那场会话里，我第 4 答报告了两句关于「本机」的读数：「本机 ComfyUI 目前**没装任何 SDXL checkpoint**，现有的是 qwen_image_2.1 / z_image_turbo / H3」，以及「**本机**：刚查了下 —— GB10，统一内存 ~122GiB，当前还空着 ~26GiB」。两句都取自 comfyui-mcp。**本轮实测我真正的宿主**：`free -m` → total **3861 MB** / available **978 MB**；`uptime` → **13d21h**；`ss -ltnp` → `127.0.0.1:18000`(gateway) / `127.0.0.1:18790`(sandbox host) / `*:8188`（8188 那条**没有 users 列** —— 监听进程不属于本用户）。**这两组数字不是一个对象**：一个 122GiB 统一内存的 GB10 盒子，不会同时是这台 3.8GiB 的 gateway 宿主。于是同一分钟里出现**两份「账」**：一份是我的宿主（RAM 1196→966 MB 两天里往下走、`comfyui-mcp` 匹配行 21→24、node 主进程 7 个 RSS ≈730→874 MB），另一份是那场会话报的（~26GiB 空闲），两者差两个数量级 —— 而「本机」这一个词把两者缝在了一起。**根因不是算错，是「本机」这个词携带了一个未被验证的等同**：凡是对外说的「本机 / 本地 ComfyUI / 这台机器」，都默认「MCP 读到的那个 target = 我脚下这台宿主」，而这条链从来没被证过（8188 后面到底是什么，从这台机器上看不出来；MCP 的 target 也未在 `ps` 参数里暴露）。规则：**把「我看到 X 变了」推成「对象 Y 也变了」之前，先写下那个信号是「谁」发出的**；对一个能指向多台机器的工具，「本机」不是坐标，是一个待填的空 —— 写不出它的 target，就只能说工具返回了什么，不能说「我的机器」如何。写给自己的一条纪律：**两侧的读数永远分开记**，一边漂不带上另一边。与 #71（事后现场 ≠ 事发现场）同族但换了轴：#71 错在**时间方向**（拿之后的状态讲之前的故事），这条错在**对象归属**（拿此对象的状态讲彼对象的故事）；与 #60/#62（哪一份副本 / 哪一层根目录）相邻，但那两条问「我在看哪一份」，这条问「**我在看哪一台**」（2026-10-06）
