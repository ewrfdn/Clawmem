# 教训总结

从经验中提炼的规则。每条都有真实的踩坑故事做支撑。

## 技术类

1. **Ubuntu Noble 上别用 snap 装浏览器** — 速度极慢，直接用官方 deb（2026-03-26）
2. **服务器上的 Chrome 需要 headless + no-sandbox** — 否则启动超时（2026-03-26）
3. **dpkg 锁冲突时要耐心** — 别强删锁文件，等上一个进程结束（2026-03-26）
4. **所有技能必须存储在 GitHub** — 在 Clawmem/skills 中开发，按需加载到 workspace，不在 workspace 里直接写技能（2026-03-27）
5. **路由器透明代理 ≠ PC 客户端配置** — fancyss 等插件用 TPROXY/iptables redirect，不能导入 socks5/http 的客户端 json，要用插件界面填参数（2026-03-31）
6. **Let's Encrypt 证书指纹会变** — 90 天续期后 pinnedPeerCertSha256 失效，不建议填（2026-03-31）
7. **排查网络问题先看日志有没有流量** — access.log 为空 = 流量没到服务端，直接定位断点在客户端/中间层（2026-03-31）
8. **nginx 访问用户目录要检查整条权限链** — 每级目录都需要 nginx 用户可读/可执行，700 的 home 目录会挡住一切（2026-04-07）
9. **敏感配置值只写引用路径** — MEMORY.md 等公开可能性高的文件里只写「见 /etc/xxx」，不写实际 UUID/密码（2026-04-07）

## 工作方式类

1. **先跑起来再优化** — 完美的设计不如能用的实现（2026-03-26，snap vs deb 的教训）
2. **写下来** — 每个没记录的想法都等于没有（2026-03-26，初始化记忆系统的感悟）
3. **先在 Clawmem 开发技能，再加载到 workspace** — 保持单一来源（2026-03-27）

10. **OpenClaw 频道配置要显式启用** — 不要依赖 guild 级别 fallback，每个需要响应的频道都必须在 guilds.channels 里显式配置 `enabled: true`（2026-04-16）
11. **同一频道 session 是串行的** — webchat 和 Discord 如果共享同一个 session key，处理一边时另一边会排队/丢失消息。不同频道间才是并行的（2026-04-16）
12. **token/密钥不要在聊天中明文粘贴** — 一旦粘贴就视为已泄露，必须立即轮换（2026-04-16）
13. **Channel ID 要对应正确的 Guild** — 放错 guild 下会导致消息路由完全失败，排查时先确认 channel 归属的 guild ID（2026-04-16）
14. **cron isolated session 里 PATH 要显式 export** — 子进程不继承主 shell 的 PATH，所有 cron prompt 开头加 `export PATH=$HOME/.local/bin:$PATH`（2026-04-21）
15. **heredoc 会占用 stdin** — `python3 - <<'HEREDOC'` 在管道场景下不可用，用 `python3 -c '...'` 代替（2026-04-21）
16. **东方财富接口偶发 403** — 数据抓取脚本必须有容错和跳过逻辑，不能因单个接口挂掉整个流程（2026-04-21）

## 方法论类

17. **A 股基本面分析要区分归母和扣非** — 归母净利润包含非经常性损益（政府补贴/资产处置），扣非才反映真实主业盈利能力。看到两者差距大就要追问来源（2026-04-24）
18. **产业链价值分布决定标的选择** — 同一条产业链里，整机组装(8-15%毛利) < 算力租赁(20-30%) < 软件/应用(50-70%)。投资要选利润率高的环节（2026-04-24）
19. **Discord allowBots 配置** — 要看到其他 bot 的消息（比如 Kagura @ 我），需要设 `allowBots: "mentions"`，默认会过滤掉 bot 消息（2026-04-25）
20. **A股自动选股范围必须限沪深主板** — 创业板/科创板可以分析参考，但不能纳入实际买入候选和持仓更新。盘前/盘中/盘后所有环节都要遵守此边界（2026-05-06）
21. **伪多样性是实验设计的隐藏坑** — 当模型产出看起来多样的结果时，要检查是否只是适应了评价标准。包括自己做实验时也一样（2026-05-15）
22. **逻辑顺序不等于认知顺序** — 写规则/说明时，先处理读者焦虑和误解，再展开完整逻辑；否则正确的论证顺序也会制造抵触（2026-06-07）
23. **梯度设计首先是激励设计** — 多一个选项不只是分类更细，而是改变选择者的动机结构；设计协议时要问“这个选项会成为逃逸口还是降低正确行动门槛”（2026-06-09）
24. **协议记录要控制粒度** — 不是所有分叉都值得登记；只记录改变路径、责任归属或解释成本的节点，否则正式文本会退化成维护手册（2026-06-12）
25. **并行草稿先局部成型，再低粒度对齐** — 太早对齐会压平协作者的局部判断；先保留各自草稿形状，再处理接口与术语层面的对齐（2026-06-12）
26. **记录是诊断数据，不是自动干预命令** — 可枚举分叉值得进入 review 视野，但如果每个分叉都触发治理，协议会变重并诱发防御性写作（2026-06-13）
27. **共享可见性先于干预** — 结构性问题先让相关协作者共同看见，再决定是否处理；直接把可诊断信号变成干预，会放大防御成本并压缩真实分歧（2026-06-14）
28. **OpenClaw 工具不是 shell 命令** — `apply_patch` 是 OpenClaw 工具，不一定存在本地二进制；改文件要直接调用工具，不要把工具语义塞进 `exec` 的 shell heredoc（2026-06-15）
29. **好的记录追求可验证理解，不追求完全免猜** — 决策账和附注的目标是让后来协作者能验证自己是否理解了当时的判断入口，而不是把所有语境都写成不可错读的维护手册（2026-06-15）
30. **退场也要设计边界** — 低占用退出不是“以后随时回来继续管”，而要限制未来重入范围；不接管必须成为对方可观察的约束（2026-06-19）
